Member 05 · agent money · built 2026-11

A wallet an agent can hold.

If you give an AI agent money, the first question anyone with money asks is what stops it draining the account. This is the answer, in two layers that do not depend on each other.

Ask about it See all members →

Layer one · the software gate

Five rules before a payment is allowed to exist.

Within budget

A payment over the stated ceiling is refused as OVER_BUDGET.

Evidence exists

A spend with nothing behind it is refused as NO_EVIDENCE.

Recipient allowed

A payment to anyone off the list is refused as RECIPIENT_NOT_ALLOWED.

Purpose specific

A vague reason is refused as PURPOSE_TOO_VAGUE.

Amount real

Zero or negative is refused as AMOUNT_NOT_POSITIVE.

Exact arithmetic

Amounts are computed in decimal, not floating point. One half of a NEAR token becomes exactly 500000000000000000000000 yoctoNEAR, never a rounding artefact.

A refusal is not a crash. It is a named outcome with a reason attached, written to the same record as an approval. The gate is tested in both directions: honest payments pass, every violation above is refused.

Layer two · the chain-enforced key

Even if the software is bypassed, the chain still refuses.

The key the agent holds is scoped at the protocol level. It may call one function on one contract, up to one allowance. It cannot send anywhere else, and it cannot exceed the ceiling, because the network enforces those limits rather than our code.

That matters because a software gate is a promise and a scoped key is a constraint. A promise can be patched around. A constraint held by the chain cannot.

This was verified on NEAR testnet, not assumed: the account exists, the scoped key exists, and the stored allowance, method name and receiver match what the builder produces.

Verified on testnet

Account created, funded, and a function-call key added with a fixed allowance, a single permitted method and a single permitted receiver.

Layer three · the receipt

A record that cannot be quietly edited.

Every approved payment writes a receipt, and every receipt carries the hash of the one before it. Edit a receipt and the chain breaks. Remove one and the chain breaks. Anyone holding the file can check it without trusting the party that produced it.

That is the difference between a log and a record. A log says what someone wrote down. A record can prove it was not rewritten afterwards.
